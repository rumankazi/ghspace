Schema lives in `packages/core/src/db/schema.ts`. Migrations are generated by
Drizzle Kit into `packages/core/drizzle/`.

## Shape

```
users ─┬─ github_credentials        encrypted user tokens
       ├─ user_installations        which installations this user reaches
       ├─ user_repository_access    ★ the security boundary
       └─ pull_request_involvement  why this user cares about a PR

installations ── repositories ── pull_requests ─┬─ pull_request_reviews
                                                ├─ pull_request_review_requests
                                                └─ pull_request_assignees

sync_runs        one row per sync attempt, user- or installation-scoped
```

## Shared versus tenant-scoped

This distinction drives everything.

**Shared** — `installations`, `repositories`, `pull_requests`, and the three
pull request child tables. Keyed by GitHub's own node ids and deduplicated
globally. If two ghspace users can see the same pull request, it is stored once
and refreshed once. This is what makes one installation sync serve a whole
organisation.

**Tenant-scoped** — `users`, `github_credentials`, `user_installations`,
`user_repository_access`, `pull_request_involvement`. Everything specific to one
person's view.

Every tenant-scoped table has been scoped since the first commit, even while
there is one user. Opening ghspace to other people should be a UI change, not a
migration.

## `user_repository_access`

<Callout type="error">
Not a convenience index. Pull requests are cached with an installation token
that can read every repository in the account; this table is the only thing that
knows which of them a given user is entitled to. See
[Access model](/docs/access-model#the-security-boundary).
</Callout>

## `pull_request_involvement`

Denormalises the derived `bucket` onto the row, so the read path is an indexed
lookup rather than a per-request recomputation across joins.

`isMentioned` exists but is always `false` under the current sync — only the
search-based recovery path can populate it. It is kept rather than dropped
because that path may return.

## `sync_runs`

One row per attempt, with both `user_id` and `installation_id` nullable —
installation syncs have no user, access syncs have no installation.

Two jobs:

1. **Honesty about staleness.** The UI shows "synced 4m ago" from here. The
   figure reported is the *oldest* of the most recent successes across the
   user's installations, because one stale installation makes the whole page
   stale.
2. **Rate limit observability.** Each run records GitHub's `cost`, `remaining`
   and `resetAt`, so budget burn is visible in the UI before it starts causing
   failures.

## Conventions

- `casing: "snake_case"` in the Drizzle config — TypeScript stays camelCase,
  the database stays snake_case.
- Enum-ish columns are `text` with `$type<...>()` rather than Postgres enums, so
  a new value is a code change rather than a migration.
- Upserts use `ON CONFLICT DO UPDATE` with `excluded.*`. Values are always
  deduplicated first: Postgres rejects a statement that would touch the same row
  twice.
- Bulk inserts are chunked at 500 rows; Postgres caps a statement at 65,535 bind
  parameters.
