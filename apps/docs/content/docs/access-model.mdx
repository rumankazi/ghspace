This is the page most worth reading carefully. The token model is easy to get
wrong, and getting it wrong leaks private repositories.

## A GitHub App only sees where it is installed

From the [GitHub documentation](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-with-a-github-app-on-behalf-of-a-user):

> The app can only access resources in an account where it is installed. If your
> app is only installed on a user's personal account, it cannot access resources
> in an organization that the user is a member of unless the app is also
> installed on that organization.

<Callout type="warn">
This applies to **user access tokens too**. A user-to-server token's reach is
the *intersection* of what the app has via installations and what the user can
personally see. It is not a way around installation scope.
</Callout>

So requiring users to install ghspace on their organisations is the product's
onboarding, not a limitation to design around. Every tool in this space works
the same way, for the same reason.

The dashboard surfaces its own coverage — which accounts are connected, how many
repositories each exposes — so a missing organisation reads as a setting rather
than a bug.

## Two tokens, two jobs

| | Installation token | User token |
| --- | --- | --- |
| Acts as | the app itself | the signed-in user |
| Sees | everything the installation granted | installation ∩ that user's own access |
| Rate limit | 5,000/hr **dedicated**, scaling to 12,500 by account size | 5,000/hr **shared** with every other app acting for that user |
| Needs user online | no | yes — plus token refresh |
| Used for | fetching pull requests | identity, and the access allowlist |

Note the rate limit row. It is the opposite of what intuition suggests: the
installation token has the private pool, and the user token shares one with
every OAuth app the person has ever authorised. That is one reason pull request
fetching uses installation tokens.

## The security boundary

An installation token can read **every repository in the installation**. If an
organisation installs ghspace across all its repos, that token sees things
individual members do not.

So there is exactly one thing standing between users:

```ts title="packages/core/src/dashboard.ts"
function visibleToUser(userId: string) {
  return exists(
    db().select({ one: sql`1` })
      .from(userRepositoryAccess)
      .where(and(
        eq(userRepositoryAccess.userId, userId),
        eq(userRepositoryAccess.repositoryId, pullRequests.repositoryId),
      )),
  );
}
```

<Callout type="error">
**Every read path that returns pull requests must compose `visibleToUser`.**
Omitting it on a new query would silently leak private repositories between
users of the same organisation. This is the single most dangerous thing to get
wrong in the codebase.
</Callout>

`user_repository_access` is built by `syncUserAccess`, which calls
`GET /user/installations/{id}/repositories` with **that user's own token** — the
only call that knows what one person is entitled to. Rows not reasserted by a
run are swept, which is how revoked access actually takes effect.

## Onboarding flow

Because installation *is* the onboarding, the sign-in flow has to carry it.
A user with no installations is sent to `/setup` rather than to an empty
dashboard, and every install link in the interface points at
`/api/auth/install` rather than at GitHub directly.

That indirection buys two things.

### The `state` parameter, and where it disappears

`/api/auth/install` issues a `state` and appends it to the install URL. GitHub
[returns it after the install](https://docs.github.com/en/apps/sharing-github-apps/sharing-your-github-app),
so a site-initiated install is CSRF-protected exactly like a normal sign-in.

An install begun on **GitHub's own app page** cannot be. With *"Request user
authorization (OAuth) during installation"* enabled, GitHub builds the
`/login/oauth/authorize` URL itself and redirects to the first callback URL
with only a `code` — ghspace never got to issue a state, so none comes back.

<Callout type="warn">
The callback must not simply skip the state check when one is missing. The
`code` is a working authorization code, so accepting it unverified would let a
crafted link sign a victim's browser in **as the attacker**.
</Callout>

So a callback carrying `setup_action` but no valid state is redirected to
`/api/auth/login`, starting a fresh, state-protected round trip. The user sees
nothing: GitHub does not prompt again for an app they just authorised. Before
this existed, that path failed outright with *"Sign-in link expired or was
tampered with"* — installing from GitHub's app page was a dead end.

### `installation_id` is not evidence

GitHub is explicit that
[the parameter can be spoofed](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/about-the-setup-url)
and must not be relied on. ghspace uses it for nothing at all; `setup_action`
is read only as a hint that *an* install happened.

What it actually believes comes from `syncUserAccess`, which asks GitHub with
that user's own token. The callback runs it when an install just happened or
when the user has no coverage yet, which is also what makes a fresh
installation visible: `user_installations` is written there and nowhere else,
and `listInstallationsForSync` joins through that table — so without this, the
worker would never learn the new installation existed and the user would have
to press Refresh to bootstrap themselves.

It is deliberately skipped for a returning user who already has coverage, whose
access is already known; re-listing it on every sign-in would spend their
personal rate limit to learn nothing. The pull request sync is left to the
worker rather than run inline, since a large organisation can take tens of
seconds — long enough to exceed a serverless function timeout.

## Token lifecycle

**User tokens** expire in roughly 8 hours, refreshed with a token valid for
about 6 months. GitHub **rotates the refresh token on every use**, so the new
pair is persisted *before* the access token is handed out — if that write failed
after a successful refresh, the old refresh token would already be dead and the
user would be locked out.

**Installation tokens** last an hour and are minted on demand from the app's
private key. `@octokit/auth-app` handles minting, caching and renewal, so they
are never stored.

Tokens at rest are AES-256-GCM encrypted under `ENCRYPTION_KEY`, in a `bytea`
column so nothing can log them as a readable-looking string.

## Enterprise Server

`apiBaseUrl` is stored per user and threaded through every client constructor,
so pointing ghspace at a GitHub Enterprise Server install is configuration
rather than a code change. This costs almost nothing now and would be expensive
to retrofit.

## Open question

GitHub Apps have *"implicit permissions to read public resources when acting on
behalf of a user"*, but the documentation does not say whether that reaches
**public repositories in accounts where the app is not installed**. A
[community thread on exactly this](https://github.com/orgs/community/discussions/116677)
went unanswered.

It decides whether open-source contributions appear for repositories you cannot
install on. Worth settling empirically rather than designing around either
answer.
