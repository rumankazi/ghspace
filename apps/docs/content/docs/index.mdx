ghspace is a GitHub workspace: repositories, pull requests and Actions in one
place. The first feature — and the only one built so far — is **pull request
triage**.

GitHub tells you a pull request exists. It does not tell you which ones are
*yours to move*. ghspace sorts everything you can see into buckets that answer
one question: what should I do next?

## The three decisions

Almost everything in the codebase follows from three choices. If you only read
one page of these docs, read this list.

### 1. Postgres is the cache-of-record

Page renders read only from the database, never from the GitHub API. A GitHub
outage or a rate limit degrades the dashboard to *slightly stale data with a
visible "synced 4m ago" marker*, rather than to an error page.

This is why there is a worker process at all, and why every read function in
`packages/core/src/dashboard.ts` touches nothing but Postgres.

### 2. The GitHub App is the query point

Pull requests are fetched **per installation**, not per user. One sync of an
organisation serves every ghspace user in it, runs with nobody signed in, and
spends a rate limit budget dedicated to that installation.

Users then filter the cached data — which is a database query, not another API
call. See [Access model](/docs/access-model).

### 3. Involvement is derived, not asked for

Because the sync fetches repositories whole, "which pull requests involve me" is
computed locally from data already held: who opened it, who is assigned, whose
review is pending, who has reviewed.

This has [real limits](/docs/sync-pipeline#what-this-model-cannot-see) — mentions
and team review requests are invisible — and those limits are a deliberate
trade, not an oversight.

### A fourth, about where it runs

ghspace depends on Postgres and nothing else about its host. A free managed
database and a self-hosted container are one line of `.env` apart, which is a
property that has to be [actively defended](/docs/portability) rather than
assumed.

## The buckets

| Bucket | Means |
| --- | --- |
| **Blocked on you** | Waiting on you — a requested review, or a change to a repository you own |
| **Needs your action** | Changes requested, failing checks, or a merge conflict on your work |
| **Ready to merge** | Approved, green, mergeable |
| **Blocked on others** | Your open pull requests waiting on a review |
| **Your drafts** | Work in progress you have not opened for review |
| **Watching** | You are assigned, or have already reviewed |
| **Dependency updates** | Automated bumps in repositories you own |

The rules live in one pure function, `classify()` in
`packages/core/src/sync/buckets.ts`, so they are cheap to test and easy to argue
about. They are covered by unit tests.

### Why bots get their own bucket

GitHub does not consider you "involved" in a Renovate or Dependabot pull request
in your own repository — you did not open it, you are not assigned, and no
review was requested of you. For a solo developer that omits most of the real
queue, since nobody else is going to merge those.

`isRepositoryOwner` supplies the missing signal, and bot-authored bumps get
their own bucket rather than flowing into the ordinary ones: there are usually
many of them and they are a different kind of work from reviewing a colleague's
change.

<Callout type="warn">
That rule is checked **before** review requests, which looks wrong until you see
real data. Renovate and Dependabot are routinely configured with `reviewers:`
and `assignees:`, so honouring those signals funnels the entire dependency queue
into "Blocked on you" and destroys the separation. On the author's own account,
9 of 38 bumps carried an automated review request.
</Callout>

The bucket opens collapsed, but its closed header still reports how many pull
requests are failing or conflicting, and those sort first inside it — a broken
bump must not be able to hide behind thirty green ones.
